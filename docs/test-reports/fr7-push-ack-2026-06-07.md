# FR7 push-ack load result (organiser edit fan-out)

Records the FR7 run (`tests/load/scenarios/organiser_edit.js`) against the
**deployed AWS stack**. FR7: when an organiser edits an event, every RSVP'd
attendee is notified through the relay -> SNS -> SQS -> Lambda fan-out within the
push-ack SLO (p95 <= 5 s, p99 <= 10 s, ADR-0011), while concurrent map traffic
continues. Runbook and method: [`tests/load/README.md`](../../tests/load/README.md).

## Verdict: PASS

At N = 300 RSVP'd attendees, the edit fan-out delivered to all 300 within the
SLO under concurrent map load.

## HTTP-measured SLO (asserted by k6)

The one-shot edit fires 45 s into a sustained 50 req/s map-query load; k6 asserts
the concurrent map path stays healthy.

| Metric | SLO | Measured | Verdict |
| --- | --- | --- | --- |
| concurrent map-query error rate | < 1 % | 0.00 % (0 / 5997) | PASS |
| concurrent map-query p99 (client) | <= 500 ms server-side | 1.13 s client-observed | see note |

Note: the harness ran from Australia against `us-east-1`, so the client-observed
map latency carries trans-Pacific RTT and is not the 500 ms server-side figure
(same caveat as `load-test-2026-06-06.md`); the GEO_P99_MS threshold was set to
2000 ms for the out-of-region run. The map path served 5997 requests with zero
errors throughout the fan-out, which is the point of this assertion - the edit
spike did not degrade concurrent map traffic.

## Push-ack fan-out (measured from worker CloudWatch logs)

k6 cannot time the async fan-out. push-ack is measured as the spread between
`edit_at` and each worker `Notification ack: ... type=event_updated` line for
this `event_id` (filtered to `type=event_updated`, since RSVP seeding also emits
`rsvp_placed` acks for the same event). Computed from the raw ack timestamps.

| N (attendees) | delivered | p50 | p95 (SLO <= 5 s) | p99 (SLO <= 10 s) | max | Verdict |
| --- | --- | --- | --- | --- | --- | --- |
| 300 | 300 / 300 | 2.13 s | **4.60 s** | **4.77 s** | 4.82 s | **PASS** |

`delivered == 300` (no lost messages) ties FR7 back to QA3 reliability. The first
ack's CloudWatch timestamp landed ~60 ms before the k6-recorded `edit_at`
(min = -0.06 s); this is NTP skew between the k6 client clock and CloudWatch and
does not affect the percentiles.

## Measurement boundary (honest scope)

The SLO is measured at the **worker ack** - the worker logging delivery of each
per-recipient notification - which is the boundary `organiser_edit.js` and the
runbook define for this row, and the same boundary used for the QA1-load / FR5
fan-out in `load-test-2026-06-06.md`. On this deployment delivery terminates at
the worker: there is no live web-push browser subscription (the SPA push-
subscription flow is not yet built) and email uses the logging-only provider
(empty Resend key), so the worker delivered to the email-mock channel. The
measured number is therefore the relay -> SNS -> SQS -> Lambda **pipeline** latency,
not a real browser push-service ack. Wiring a true web-push subscription (or a
real Resend key) is a tracked follow-up; it does not change the fan-out timing
this run measures.

## Demonstrated scale

N = 300 matches the demonstrated scale of the QA1-load fan-out
(`load-test-2026-06-06.md`); the `organiser_edit.js` default of N = 1000 is the
target, argued by the same flat-ack-latency extrapolation. The headroom here is
smaller than QA1-load because the FR7 SLO is tighter (5 s vs 30 s): p95 = 4.6 s
leaves ~0.4 s under the 5 s budget at N = 300.
